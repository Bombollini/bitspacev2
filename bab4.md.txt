BAB IV
IMPLEMENTASI DAN PENGUJIAN

4.1	Implementasi Sistem

Implementasi sistem Bitspace mengacu pada rancangan sistem yang telah disusun pada BAB III. Sistem dikembangkan sebagai aplikasi web berarsitektur SPA (Single Page Application) dengan memakai React sebagai library pembangun antarmuka dan Supabase sebagai Backend-as-a-Service untuk menangani persistensi data, autentikasi, penyimpanan berkas, dan eksekusi kode serverless. Pemilihan arsitektur BaaS diambil dengan pertimbangan agar tim pengembang dapat lebih memusatkan perhatian pada logika bisnis domain daripada harus membangun dan memelihara infrastruktur server mandiri seperti Express atau NestJS dari nol. Tahapan implementasi diawali dengan penentuan spesifikasi perangkat keras dan lunak pendukung, kemudian dilanjutkan dengan implementasi basis data, lapisan layanan backend, lapisan antarmuka frontend, kontrol hak akses tiga lapis, Application Programming Interface, dan pengujian sistem.

4.1.1	Spesifikasi Hardware

Spesifikasi perangkat keras yang dipakai pada fase pengembangan dan pengujian Bitspace disesuaikan dengan kebutuhan siklus pengembangan aplikasi React modern yang mengandalkan build tool Vite beserta TypeScript compiler dan browser untuk menjalankan aplikasi. Selama fase pengembangan, seluruh proses berjalan secara bersamaan: editor kode sumber, dev server Vite dengan fitur HMR (Hot Module Replacement), TypeScript type-checking, dan hingga tiga instance browser untuk pengujian lintas-browser, sehingga kebutuhan sumber daya komputasi tidak dapat diabaikan begitu saja. Tanpa perangkat keras yang memadai, proses pengecekan tipe dan HMR pada Vite akan mengalami penundaan yang mengganggu produktivitas penulis.

Perangkat keras minimum yang digunakan adalah prosesor Intel Core i5 generasi ke-10 atau setara untuk menangani kompilasi dan bundling Vite secara real-time. Memori RAM sebesar 8 GB digunakan untuk menampung keseluruhan proses, mulai dari cache dependensi npm, editor dengan puluhan ribu berkas sumber, Node.js runtime, dan proses browser yang memuat source maps. Penyimpanan berbasis SSD dengan kapasitas minimal 256 GB diperlukan untuk menampung source code, folder node_modules yang mencapai ratusan ribu file, serta artefak build output. Kapasitas ini juga menyisakan ruang untuk caching dan basis data lokal untuk kebutuhan pengujian. Monitor beresolusi minimal 1920 x 1080 piksel digunakan agar antarmuka Bitspace yang mengandung panel kanban, grafik recharts, dan panel AI sidebar dapat ditampilkan tanpa scrolling berlebihan.

Koneksi jaringan internet dengan kecepatan minimal 10 Mbps diperlukan karena setiap transaksi data berjalan menuju Supabase cloud, pemanggilan Google Gemini API untuk fitur kecerdasan buatan, dan sinkronisasi bucket storage Supabase. Koneksi yang tidak stabil dapat menyebabkan timeout pada autentikasi Supabase Auth, kondisi yang telah diantisipasi oleh wrapper fetchWithTimeout di sisi client agar aplikasi tidak mengalami pembekuan antarmuka yang tak kunjung pulih. Lingkungan produksi hanya membutuhkan perangkat pengguna biasa berupa komputer laptop atau ponsel cerdas dengan browser modern yang mendukung ECMAScript 2022, sebab aplikasi Bitspace di-build menjadi berkas statis HTML, CSS, dan JavaScript yang dapat diunggah ke CDN mana pun tanpa ketergantungan server aplikasi.

4.1.2	Spesifikasi Software

Spesifikasi perangkat lunak disusun agar setiap anggota tim pengembang dapat mereproduksi lingkungan pengembangan yang identik tanpa inkonsistensi versi perangkat lunak. Reproducibility lingkungan pengembang menjadi krusial sebab Bitspace memakai banyak dependensi yang sensitif versi seperti React 19 dan Vite 6 yang konfigurasi build-nya berbeda dari rilis major terdahulu. Sistem operasi pengembangan menggunakan Windows 10 atau versi lebih baru sebagai basis utama pengembangan, sebab berkas paket berisi dependency management Node.js dan script npm dapat dijalankan tanpa masalah. Runtime Node.js versi 16 atau lebih baru menjadi persyaratan utama sebab Vite 6 memakai API Node.js versi terbaru pada internal build tool-nya. Package manager yang dipakai adalah npm yang terintegrasi secara langsung dengan Node.js.

Sebagai editor sumber daya utama penulisan kode dipakai Visual Studio Code yang dilengkapi ekstensi resmi TypeScript dan ESLint serta formatter Prettier untuk menjaga konsistensi gaya penulisan kode. Pengujian antarmuka dilakukan pada tiga browser modern yaitu Google Chrome, Mozilla Firefox, dan Microsoft Edge pada rilis stabil terbaru, guna memastikan kompatibilitas rendering Tailwind, drag-and-drop HTML5 pada TaskCard, dan penyimpanan localStorage sesi autentikasi Supabase. Pengujian pada lebih dari satu browser bertujuan menangkap perbedaan perilaku implementasi API browser, misalnya perilaku drag event pada Firefox yang sedikit berbeda dari Chrome.

Daftar pustaka sisi client tercatat dalam file package.json. Library inti terdiri dari React 19.2.3 dan React DOM 19.2.3 sebagai library rendering antarmuka. TypeScript 5.8.2 menyediakan type safety dan static analysis saat penulisan kode sehingga kesalahan tipe data dapat dideteksi sebelum memasuki fase runtime. React Router DOM 7.11.0 menyediakan routing pada aplikasi SPA. Pemilihan HashRouter alih-alih BrowserRouter didasarkan pada kebutuhan deployment static hosting yang tidak selalu menyediakan konfigurasi fallback history API, sehingga aplikasi dapat berjalan pada Supabase Storage, Vercel, dan Netlify tanpa konfigurasi server tambahan. Pustaka pendukung antarmuka lainnya adalah lucide-react 0.562.0 sebagai penyedia ikon konsisten, recharts 3.9.2 untuk visualisasi diagram batang dan pai pada DashboardPage dan komponen AnalyticsCharts, react-markdown 10.1.0 untuk merender output sprint report dan chat AI workspace yang dihasilkan fitur kecerdasan buatan, serta canvas sebagai dependensi tidak langsung untuk SVG processing. Library utilitas terdiri dari axios 1.13.2 sebagai HTTP client generik, jspdf 4.0.0 bersama plugin jspdf-autotable 5.0.7 untuk kebutuhan pembangunan laporan PDF, serta svg2img dan glob sebagai utilitas pendukung pada fase pembangunan wireframe dokumentasi.

Lapisan backend memakai Supabase sebagai Backend-as-a-Service yang mencakup PostgreSQL 15 sebagai engine basis data relasional, Supabase Authentication untuk manajemen kredensial dan hashing bcrypt, Supabase Storage untuk bucket avatars dan task_attachments, dan Supabase Edge Functions dengan runtime Deno untuk menjalankan kode serverless send-meeting-email. Integrasi kecerdasan buatan secara langsung memakai Google Gemini API versi 2.5 Flash melalui panggilan fetch HTTPS langsung dari kelas AIService tanpa middleware backend Node.js terpisah. Keputusan pemanggilan langsung diambil agar arsitektur lebih sederhana mengingat respons Gemini tidak memerlukan transformasi data tambahan antara client dengan model AI. File konfigurasi vite.config.ts menetapkan port development 3000 dengan host 0.0.0.0 agar perangkat mobile pada jaringan LAN yang sama dapat mengakses aplikasi untuk pengujian, alias path @ mengarah ke root proyek guna memudahkan impor modul lintas direktori, dan define environment variables process.env untuk kompatibilitas dengan library yang masih memakai variabel environment gaya process.env.

4.2	Implementasi Database

Implementasi basis data Bitspace dibangun di atas PostgreSQL 15 yang dikelola platform Supabase. Seluruh struktur basis data didefinisikan melalui file SQL migrasi terpisah agar perubahan skema dapat direplikasi secara berulang pada environment pengembang lain tanpa risiko modifikasi manual melalui GUI. Struktur utama basis data secara lengkap didefinisikan dalam supabase_full_schema.sql yang berisi definisi enumerasi, definisi tabel, fungsi bantuan keamanan, Row Level Security policies, storage bucket policies, dan trigger sinkronisasi profil. Selanjutnya, pengembangan fitur tambahan milestone, meeting, lampiran tugas, summarization AI meeting, sub-tugas, dan analisis kesehatan proyek didefinisikan masing-masing dalam berkas migrasi milestones_migration.sql, meetings_migration.sql, task_attachments_migration.sql, meetings_ai_migration.sql, subtasks_migration.sql, dan project_insights_migration.sql. Pendekatan migrasi bertahap ini memudahkan pelacakan riwayat penambahan fitur selama proses pengembangan berjalan.

Sebelum pembuatan tabel, didefinisikan lima tipe enumerasi PostgreSQL untuk membakukan domain nilai kolom yang tetap. Lima enumerasi tersebut adalah user_role dengan tiga nilai OWNER, ADMIN, dan MEMBER untuk level aplikasi global; project_status dengan dua nilai ACTIVE dan ARCHIVED; task_status dengan lima nilai BACKLOG, TODO, IN_PROGRESS, REVIEW, DONE untuk alur Kanban; task_priority dengan tiga nilai LOW, MEDIUM, HIGH; dan enumerasi member_role dengan tiga nilai OWNER, EDITOR, VIEWER untuk kebutuhan perluasan hak akses tingkat proyek di kemudian hari. Penggunaan enumerasi memastikan konsistensi data di tingkat engine basis data dan menghindari kesalahan penulisan string case-sensitive seperti 'Todo' alih-alih 'TODO' karena PostgreSQL otomatis menolak nilai di luar daftar enumerasi.

Tabel profiles menyimpan data profil pengguna bisnis yang tidak tersedia pada tabel auth.users internal Supabase. Tabel profiles memiliki id UUID primary key yang merujuk ke auth.users dengan constraint on delete cascade agar profil ikut terhapus jika akun autentikasi dihapus. Kolom email, full_name, avatar_url menyimpan data identitas pengguna. Kolom role bertipe enumerasi user_role dengan default MEMBER, sehingga pengguna baru yang mendaftar tanpa penetapan eksplisit otomatis menjadi anggota biasa. Dua kolom created_at dan updated_at menyimpan timestamp perubahan. Supabase auth.users hanya menyimpan email, password hash, dan metadata autentikasi dasar, sehingga pemisahan profil ke tabel public.profiles diperlukan agar aplikasi dapat memodifikasi profil dan menambahkan kolom tambahan tanpa menyentuh skema internal Supabase yang tidak dirancang untuk dimodifikasi pengguna.

Tabel projects menyimpan data proyek. Primary key id UUID di-generate otomatis melalui gen_random_uuid() pada setiap baris baru. Kolom name dan description menyimpan narasi proyek, owner_id merujuk ke id profil sebagai pemilik, status bertipe project_status dengan default ACTIVE, serta project_goal, team_size, deadline, generated_by_ai, project_context menyimpan konteks untuk fitur generator AI. Setiap kali proyek diakses melalui fungsi projects.list() atau projects.get(), client melakukan join agregat ke tabel tasks untuk menghitung totalTasks, completedTasks, dan overdueTasks yang kemudian dimasukkan ke dalam properti stats pada setiap objek proyek. Perhitungan ini tidak disimpan secara fisik dalam basis data agar selalu mencerminkan kondisi tugas terbaru.

Hubungan many-to-many proyek dan anggota disimpan dalam tabel project_members dengan composite primary key project_id dan user_id, sehingga satu pengguna tidak dapat didaftarkan dua kali pada proyek yang sama. Tabel tasks berisi kolom id, project_id, milestone_id nullable, title, description, status, priority, assignee_id, due_date, attachment_url yang menampung URL lampiran pada storage, dan parent_task_id self-referencing untuk mendukung struktur sub-tugas yang dipecah melalui AI generateTaskBreakdown. Tabel activities merekam setiap perubahan data dengan kolom action_type berupa string misalnya TASK_CREATED, entity_type, entity_id, dan metadata bertipe JSONB yang menyimpan perubahan delta secara fleksibel tanpa perlu menambah kolom setiap kali ada jenis aktivitas baru. Tabel comments menyimpan komentar dengan task_id, user_id, content, dan created_at.

Tabel milestones ditambahkan setelah skema awal dengan kolom id, project_id, title, description, due_date, dan status OPEN/CLOSED agar kumpulan tugas dapat dikelompokkan berdasarkan target capaian bertahap. Tabel meetings berisi id, project_id, title, meeting_date, meeting_link, retrospective, created_by, ditambah kolom meeting_notes dan meeting_summary bertipe JSONB via migrasi terpisah untuk menyimpan output summarization kecerdasan buatan. Terakhir tabel ai_project_insights menyimpan health_score, risk_level, recommendations sebagai array JSONB, delay_prediksi dalam bentuk string, dan array bottlenecks. Rancangan berkas terpisah untuk fitur AI memungkinkan penambahan kolom ini tanpa mengganggu migrasi utama.

Row Level Security diaktifkan pada seluruh tabel utama profiles, projects, project_members, tasks, activities, comments, milestones, meetings, dan ai_project_insights. Agar evaluasi policy tidak menyebabkan rekursi tak terbatas pada saat pemeriksaan keanggotaan proyek, dibuat dua fungsi bantuan dalam bahasa PL/pgSQL dengan atribut SECURITY DEFINER. Fungsi is_admin_or_owner() memeriksa peran global OWNER atau ADMIN pengguna yang sedang aktif. Fungsi is_project_member(target_project_id) memeriksa keanggotaan pada tabel project_members tanpa mengeksekusi RLS kembali. Setiap policy disusun berlandaskan prinsip need-to-know dan minimum privilege: hanya owner_id pemilik baris, Admin global, dan anggota proyek yang diizinkan membaca data pada tabel projects. Policy Create Projects membatasi operasi INSERT hanya untuk peran OWNER dan ADMIN. Policy UPDATE dan DELETE hanya mengizinkan pemilik proyek memodifikasi baris. Pola serupa diterapkan pada seluruh tabel dengan penyesuaian domain, misalnya pada tabel comments setiap pengguna dapat meninggalkan komentar pada tugas proyek yang dapat diaksesnya, namun hanya pembuat komentar yang berwenang melakukan modifikasi atau penghapusan.

Dua storage bucket avatars dan task_attachments keduanya dikonfigurasi sebagai bucket publik agar URL file dapat diakses langsung oleh tag HTML tanpa perlu presigned URL. Policy storage untuk bucket avatars membolehkan INSERT jika auth.role() bernilai authenticated; SELECT bersifat publik agar foto profil dapat ditampilkan pada daftar anggota tanpa otorisasi tambahan. Trigger PL/pgSQL handle_new_user() dijalankan setiap kali terjadi INSERT pada auth.users: trigger on_auth_user_created mengekstrak field full_name dan role dari raw_user_meta_data lalu memasukkan baris profil baru ke public.profiles secara otomatis. Sinkronisasi trigger ini memastikan profil selalu tersedia setiap kali pengguna baru selesai mendaftar, sehingga penulis tidak perlu melakukan sinkronisasi manual dari sisi aplikasi setelah panggilan sign-up selesai.

4.3	Implementasi Backend

Backend Bitspace tidak dibangun sebagai server mandiri terpisah melainkan memanfaatkan sepenuhnya layanan platform Supabase. Pendekatan Backend-as-a-Service ini mengurangi kompleksitas infrastruktur sebab pengelolaan server, penyeimbangan beban, dan replikasi basis data sepenuhnya dikelola oleh Supabase. Secara logika, backend Bitspace terdiri dari empat komponen utama: Supabase Authentication untuk pengelolaan identitas, PostgreSQL beserta RLS untuk keamanan data, Edge Function serverless untuk pengiriman email notifikasi meeting, dan kelas AIService yang berkomunikasi langsung dengan Google Gemini API. Klasifikasi AIService sebagai bagian backend didasarkan pada perannya yang mengatur alur data bisnis dan berkomunikasi dengan API eksternal, meskipun kode fisiknya berjalan pada browser pengguna.

Modul Supabase Authentication diinisialisasi dalam supabaseClient.ts dengan konfigurasi persistSession bernilai true agar sesi tetap ada di localStorage meskipun browser ditutup kembali, autoRefreshToken true agar token akses yang kedaluwarsa diperbarui secara otomatis oleh SDK, serta detectSessionInUrl diatur true agar alur pemulihan password dapat memproses token yang dibawa kembali oleh Supabase melalui parameter tautan email pengguna. Kredensial pengguna disimpan menggunakan bcrypt internal pada tabel auth.users Supabase, sehingga hash password tidak pernah menyentuh kode aplikasi sama sekali. Alur autentikasi login, sign up, dan reset password sepenuhnya dikelola oleh SDK Supabase dengan minimal intervensi kode tambahan.

PostgreSQL RLS bertindak sebagai sumber otoritas tunggal otorisasi. Setiap SELECT, INSERT, UPDATE, DELETE yang dikirimkan client-side akan otomatis difilter melalui evaluasi policy PostgreSQL sesuai identitas auth.uid() sebelum hasil query dikembalikan. Mekanisme ini menjamin bahwa seorang anggota peran MEMBER tidak dapat melihat proyek orang lain bahkan ketika ia memaksa pemanggilan supabase.from('projects').select() secara langsung dari konsol DevTools. Upaya penghapusan proyek milik orang lain pun akan langsung ditolak oleh engine PostgreSQL tanpa perlu pengecekan tambahan di lapisan aplikasi. RLS secara efektif menghindari risiko kesalahan validasi pada client-side yang dapat dimodifikasi pengguna melalui alat pengembang browser.

Edge Function send-meeting-email berjalan di atas runtime Deno dan di-deploy ke lingkungan Supabase. Fungsi ini di-invoke melalui supabase.functions.invoke() dengan payload to, subject, dan html yang dibungkus di dalam namespace meetings.sendEmail(). Edge Function bertindak sebagai proxy agar RESEND_API_KEY yang tersimpan di Deno.env.get() tidak terekspos ke client bundle. Penanganan kesalahan pada fungsi ini dirancang untuk tetap mengembalikan status HTTP 200 meskipun email gagal dikirim. Tujuan pendekatan graceful degradation ini adalah agar kegagalan pengiriman email tidak membatalkan data meeting yang sudah terlebih dahulu tersimpan di basis data, sebab penyimpanan meeting secara teknis telah berhasil sebelum panggilan ke email.

Kelas statis AIService yang didefinisikan pada ai.service.ts menyediakan enam metode utama. Metode generateProject() menerima deskripsi proyek, ukuran tim, dan tenggat waktu proyek, lalu mengirim prompt melalui POST ke endpoint generateContent Gemini 2.5 Flash untuk menghasilkan JSON berisi struktur proyek, daftar milestone, dan daftar tugas secara terstruktur. Metode generateTaskBreakdown() memecah pekerjaan rumit menjadi sub-tugas dan kriteria penerimaan (acceptance criteria). Metode analyzeProjectHealth() memproses statistik proyek menjadi skor kesehatan, level risiko, daftar rekomendasi, prediksi keterlambatan, dan daftar bottlenecks. Metode summarizeMeeting() mengubah catatan meeting mentah anggota tim menjadi summary, keyDecisions, dan actionItems untuk disimpan ke kolom JSONB. Metode generateSprintReport() menghasilkan laporan status dalam format Markdown yang kemudian dirender react-markdown. Terakhir chatWithWorkspace() menjawab pertanyaan pengguna berdasarkan konteks proyek aktif yang diinjeksikan ke sistem prompt.

Enam metode di atas membangun prompt sesuai kebutuhan domain, menerapkan temperature 0.2 untuk tugas factual seperti summarization dan 0.7 untuk tugas kreatif seperti pembangkitan rencana proyek, memaksa responseMimeType ke JSON agar keluaran selalu dalam format yang dapat diparsing, serta memanggil parseJsonResponse dengan tiga strategi pencadangan: mencoba parsing JSON langsung, menghapus pagar pembatas ``` jika AI membungkus JSON dalam blok kode Markdown, dan regex ekstraksi blok kurung kurawal apabila kedua strategi sebelumnya gagal. Validasi akhir melalui validateAndMapResponse memastikan struktur keluaran sesuai antarmuka TypeScript, priority fallback ke MEDIUM apabila tidak dapat dipetakan, serta estimatedDays di-clamp ke rentang 1 sampai 100 agar menghindari nilai ekstrim yang tidak masuk akal dari output generatif.

Lapisan layanan client pada apiClient.ts mengelompokkan seluruh fungsi operasi data ke dalam sepuluh namespace yaitu auth, profiles, projects, tasks, milestones, activity, meetings, insights, search, dan admin. Setiap fungsi di dalam namespace bertanggung jawab membangun query Supabase berupa select, insert, update, delete, kemudian memetakan konvensi penamaan snake_case PostgreSQL ke camelCase sesuai antarmuka TypeScript melalui fungsi pembantu mapProject dan mapTask. Fungsi CREATE dan UPDATE menyisipkan log kegiatan ke tabel activities secara implisit, misalnya setelah tasks.create() berhasil dieksekusi, kode otomatis memasukkan baris dengan action_type=TASK_CREATED, entity_type=TASK, entity_id tugas baru, dan metadata berisi judul tugas. Namespace admin menyediakan getAllUsers, getAllProjects, getAllMeetings, updateUserRole, deleteProject, deleteMeeting, dan deleteUser yang semuanya diawali dengan requireAdminOrOwner() sebelum query dijalankan. Fungsi requireAdminOrOwner() menyimpan hasil pemeriksaan peran ke cachedRole selama 30 detik agar query ke tabel profiles tidak berulang pada setiap pemanggilan.

4.4	Implementasi Frontend

Aplikasi front-end Bitspace dikembangkan sebagai Single Page Application menggunakan React dan bahasa TypeScript. File index.tsx melakukan mounting root elemen dengan id root yang didefinisikan di index.html. React.StrictMode membungkus komponen App selama fase pengembangan guna mendeteksi efek samping melalui mekanisme render dua kali pada komponen. Komponen App.tsx dibungkus oleh AuthProvider yang menyediakan state autentikasi ke seluruh pohon komponen, diikuti oleh HashRouter agar routing dapat berjalan pada static hosting tanpa konfigurasi fallback tambahan. Semua route kecuali /login dan /reset-password dilindungi oleh Higher Order Component ProtectedRoute yang membaca status user dan isLoading dari hook useAuth(). Loading state menampilkan spinner CSS animasi untuk menghindari halaman kosong saat pemeriksaan sesi berlangsung. Komponen AuthNavigationHandler ditambahkan untuk mendeteksi kondisi isRecoveringPassword dan secara otomatis mengalihkan pengguna ke halaman reset password ketika mode recovery aktif.

Direktori pages berisi sembilan halaman route utama. Halaman LoginPage memuat form sign in beserta tab switch ke mode sign up untuk pendaftaran pengguna baru. Halaman ResetPasswordPage menyajikan dua mode alur: mode permintaan tautan reset password melalui email dan mode perubahan password setelah token recovery valid. DashboardPage menampilkan empat kartu ringkasan proyek beserta diagram batang progres proyek dan diagram pai komposisi status tugas yang seluruh datanya dibangun dari state projects hasil fetch awal. ProjectsPage menyajikan daftar proyek yang dapat diakses pengguna beserta statistik singkat setiap proyek. ProjectDetailPage memuat sepuluh tab interaktif tasks, overview, members, activity, milestones, ai_report, insights, gantt, analytics, dan workload; halaman ini membaca projectId dari useParams, memuat proyek, anggota, aktivitas, dan milestone melalui useEffect pada saat komponen terpasang, dan memanfaatkan useRef didInitialFetch guna menghindari pemanggilan fetch ganda akibat double-render StrictMode. MeetingsPage menyajikan daftar seluruh meeting lintas proyek sedangkan MeetingDetailPage berisi catatan, retrospective, dan ringkasan meeting. ProfilePage digunakan pengguna untuk mengelola data profil dan foto avatar. Terakhir AdminDashboardPage menyediakan tiga tab users, projects, meetings yang melakukan tiga fetch paralel melalui Promise.all api.admin.getAllUsers, getAllProjects, dan getAllMeetings agar waktu muat keseluruhan halaman menjadi lebih cepat dibandingkan sequential fetch satu per satu.

Komponen Layout.tsx membungkus seluruh halaman terotentikasi dengan sidebar kiri yang memuat navigasi dan header kanan yang menyertakan fitur global search dengan debounce 500 ms sebelum memanggil api.search.global(). Navigasi sidebar disusun secara kondisional berdasarkan peran pengguna: jika user.role sama dengan ADMIN, maka navigasi Dashboard, Projects, Meetings diganti dengan tombol Admin khusus, sementara Settings tetap ditampilkan untuk semua peran. Fitur pencarian global menampilkan dropdown berisi hasil proyek dan tugas yang namanya cocok dengan kata kunci. Komponen modal meliputi NewProjectModal, CreateProjectWithAIModal, NewMeetingModal, InviteMemberModal, TaskModal, dan TaskDetailModal yang masing-masing mengelola input data sesuai domainnya. Komponen MilestoneList menampilkan daftar capaian beserta indikator progres. Komponen fungsional pendukung lainnya adalah Badge untuk penanda prioritas dan status tugas, TaskCard yang mendukung drag-drop kanban, WorkloadManager, AnalyticsCharts yang membungkus diagram recharts, GanttChart untuk visualisasi linimasa, TimeTracker pencatat waktu kerja, AIAssistantSidebar, dan AIProjectInsightsPanel.

Pengelolaan state autentikasi diimplementasikan melalui React Context API yang dikemas dalam AuthProvider pada berkas services/authStore.tsx. State internal AuthProvider terdiri dari user objek User dengan atribut id, email, name, avatarUrl, role, createdAt; accessToken; isLoading; serta isRecoveringPassword. Fungsi checkAuth() menerapkan pola withTimeout selama 3000 ms untuk panggilan getSession dan profiles.select, sehingga mencegah pembekuan antarmuka ketika jaringan lambat atau storage autentikasi mengalami korupsi. Apabila getSession melebihi batas waktu yang ditentukan, fungsi clearSupabaseAuthStorage akan menghapus semua kunci localStorage yang diawali dengan sb dan diakhiri auth-token, memungkinkan aplikasi pulih dari kondisi stuck Loading Bitspace tanpa harus menghapus data situs secara manual. Mode PASSWORD_RECOVERY yang ditangkap oleh onAuthStateChange akan mengubah isRecoveringPassword menjadi true yang kemudian dimanfaatkan AuthNavigationHandler. Fallback name ke bagian depan email (sebelum karakter @) diterapkan ketika full_name belum diisi pada tabel profiles. Sesi pengguna dipantau secara terus-menerus melalui listener onAuthStateChange untuk mengamati perubahan status autentikasi, termasuk event sign in, sign out, dan token refresh.

Pembangunan laporan PDF dikelola oleh utils/pdfGenerator.ts yang memakai pustaka jspdf dan plugin jspdf-autotable. Fungsi generateReportHeader() membangun kop laporan secara seragam berisi logo, nama perusahaan, tanggal cetak dengan locale Indonesia id-ID, judul laporan, serta garis pemisah. Sembilan fungsi generator terpisah tersedia: generateProjectSummaryPDF, generateTaskListPDF, generateMemberWorkloadPDF, generateActivityLogPDF, generateMilestoneReportPDF, generateAIReportPDF, generateAllProjectsReportPDF, generateMeetingReportPDF, generateRetrospectivePDF. Tema tabel reportTableTheme dikustomisasi agar kepala tabel berwarna biru muda dan badan tabel berwarna abu dengan border yang rapi. Styling antarmuka Bitspace secara keseluruhan memakai Tailwind CSS versi 3.x yang didefinisikan melalui direktif @tailwind base, components, utilities pada index.css. Di dalam @layer utilities didefinisikan kelas kustom glass-panel dengan efek backdrop-blur-md, neon-border-blue dan neon-text-blue beserta versi ungu untuk efek visual identik, serta scrollbar-thin yang menyesuaikan tampilan scrollbar agar sesuai tema gelap aplikasi. Palet warna keseluruhan mengusung tema glassmorphism gradien gelap dengan sentuhan neon cyan, neon ungu, dan neon magenta yang diatur pada latar body, memberikan identitas visual Bitspace yang khas dan berbeda dari aplikasi manajemen proyek konvensional.

4.5	Implementasi Hak Akses

Kontrol akses Bitspace dijalankan pada tiga tingkatan berlapis sesuai konsep pertahanan mendalam (defense in depth). Prinsip ini menjamin bahwa kegagalan perlindungan pada satu lapisan tidak serta-merta membuka kebocoran data sebab lapisan berikutnya masih memberikan proteksi. Tiga lapisan pemeriksaan tersebut secara berurutan adalah pemeriksaan peran melalui fungsi bantuan pada lapisan service, penegakan kebijakan RLS di tingkat PostgreSQL, dan penyembunyian elemen antarmuka melalui kondisional rendering pada komponen React. Perpaduan tiga lapisan ini menjadikan akses tidak sah sulit ditembus dari berbagai sudut serangan.

Enumerasi UserRole pada types.ts menetapkan tiga tingkatan peran yaitu OWNER, ADMIN, dan MEMBER. Peran OWNER diberikan kepada pemilik proyek yang berwenang membuat proyek, mengundang dan menghapus anggota, serta mengelola sumber daya seluruh proyek miliknya secara penuh. Peran ADMIN ditetapkan bagi administrator sistem yang wewenangnya melintasi batas proyek; melalui AdminDashboardPage, ADMIN dapat melihat daftar semua pengguna, semua proyek, dan semua meeting tanpa memandang kepemilikan proyek, serta melakukan perubahan peran dan penghapusan data secara administratif. Peran MEMBER merupakan peran default bagi pengguna baru; anggota biasa hanya dapat melihat proyek yang diundang ke dalamnya sebagai anggota, mengelola status tugas yang menjadi tanggung jawabnya, berpartisipasi dalam komentar dan unggah lampiran, serta melihat meeting yang terkait proyeknya.

Lapisan pertama pemeriksaan yaitu requireAdminOrOwner() yang didefinisikan dalam apiClient.ts berjalan sebelum operasi CREATE, UPDATE, dan DELETE sensitif dijalankan. Fungsi ini juga memiliki alias requireOwner() untuk kompatibilitas mundur dengan kode lama yang masih memanggil nama fungsi tersebut. Fungsi ini mengambil pengguna aktif melalui getUser(), membandingkan perannya, dan menyimpan hasil ke dalam cachedRole selama 30 detik agar pemeriksaan berulang tidak memicu query profil berlebih. Lapisan kedua adalah RLS PostgreSQL yang menegakkan kebijakan langsung di tingkat basis data. Contohnya, policy UPDATE projects mengharuskan auth.uid() sama dengan owner_id; tanpa memenuhi kondisi ini modifikasi ditolak meskipun panggilan update berhasil dikirim dari client. Lapisan ketiga diwujudkan melalui kondisional rendering pada komponen React yang menyembunyikan tombol-tombol aksi yang tidak diperbolehkan untuk peran tersebut. Pada Layout.tsx, array navigasi dikondisikan berdasarkan UserRole.ADMIN. Tombol hapus proyek, tombol undang anggota, dan tombol edit milestone hanya dirender apabila pengguna aktif berperan sebagai OWNER atau ADMIN. Pemeriksaan anggota tingkat proyek melalui project_members juga menghalangi akses langsung ke halaman ProjectDetailPage dengan terlebih dahulu memverifikasi status keanggotaan sebelum data proyek diproses lebih lanjut.

4.6	Implementasi Application Programming Interface

Application Programming Interface pada Bitspace terdiri dari dua bentuk yang saling melengkapi. Pertama adalah API internal berupa objek layanan service yang diekspor dari apiClient.ts dan projects.service.ts untuk menyediakan abstraksi operasi data agar komponen React tidak langsung berinteraksi dengan SDK Supabase. Kedua adalah HTTP API eksternal yang menghubungkan aplikasi dengan Google Gemini API dan layanan pengiriman email Resend melalui perantara. Kedua bentuk API ini bekerja sama menghubungkan komponen React dengan sumber data dan layanan luar secara terstruktur.

Objek api memuat sepuluh namespace berisi async functions yang mengembalikan Promise sesuai antarmuka TypeScript yang telah didefinisikan. Sebagai contoh projects.list() mengembalikan daftar proyek yang dapat diakses pengguna beserta join ke tabel tasks untuk perhitungan statistik, sedangkan projects.create(data) menangani penyisipan baris proyek baru dan pencatatan log aktivitas secara implisit. Komunikasi query ke basis data dilakukan melalui instance singleton supabaseClient. Klien singleton ini disimpan pada variabel global bernama __bitspace_supabase_client__ agar tidak terjadi instansiasi klien berulang pada setiap pernyataan import, yang dapat menyebabkan masalah koneksi dan kebocoran memori. Setiap permintaan HTTP dari klien dibungkus oleh fetchWithTimeout selama 15 detik menggunakan AbortController untuk memutus panggilan yang terlalu lama. API Storage pada profiles.uploadAvatar() membangun path berformat user.id/timestamp.ext, melakukan upload dengan opsi upsert true, kemudian mengambil URL publik melalui getPublicUrl dan memperbarui kolom avatar_url pada tabel profiles. Pola serupa diterapkan pada tasks.uploadAttachment() dengan bucket task_attachments. API eksternal Google Gemini API diakses melalui AIService.generateProject dan metode lain yang melakukan POST ke endpoint generateContent, sementara Resend diakses secara tidak langsung melalui proxy Edge Function agar API key tetap tersimpan aman di sisi server.

4.7	Pengujian Sistem

Pengujian Bitspace dilakukan dalam tiga tahap utama yaitu pengujian fungsional, pengujian black box, dan pengujian validasi. Ketiga kategori pengujian dijalankan pada mode development melalui perintah npm run dev yang memanfaatkan Vite development server. Pelaksanaan pengujian dilakukan penulis dengan menjalankan skenario aksi pengguna satu per satu melalui antarmuka browser. Hasil dari setiap tahapan pengujian dicatat dan dijadikan dasar untuk melakukan perbaikan bug sebelum sistem dinyatakan siap untuk fase produksi.

4.7.1	Pengujian Fungsional

Pengujian fungsional bertujuan memverifikasi bahwa setiap fungsi sistem dapat berjalan sesuai spesifikasi yang telah ditetapkan pada tahap analisis kebutuhan. Skenario autentikasi diawali dengan pengujian registrasi pengguna baru melalui formulir sign up, dilanjutkan dengan verifikasi bahwa profil pengguna baru secara otomatis terbentuk di tabel profiles berkat trigger on_auth_user_created. Setelah pengguna terdaftar, dilakukan pengujian login dengan kombinasi email dan password yang valid, lalu diperiksa apakah state user pada useAuth() terisi dengan benar. Pengujian persistensi token dilakukan dengan melakukan refresh browser dan memastikan pengguna tetap masuk tanpa perlu login ulang. Terakhir skenario pemulihan password diuji dengan menekan tombol Forgot Password pada halaman login dan memverifikasi pengguna diarahkan ke /reset-password.

Skenario manajemen proyek dimulai dengan pengujian pembuatan proyek melalui NewProjectModal, diikuti pengecekan bahwa baris baru masuk ke tabel projects dengan owner_id sesuai id pengguna aktif dan status default ACTIVE. Selanjutnya dilakukan pengujian pengeditan nama dan deskripsi proyek untuk memastikan perubahan tersimpan dan tercermin pada daftar proyek. Skenario tugas dan milestone dijalankan dengan membuat milestone pada proyek uji, kemudian membuat beberapa tugas dengan variasi status BACKLOG, TODO, IN_PROGRESS, REVIEW, dan DONE; variasi prioritas LOW, MEDIUM, HIGH; serta menetapkan assignee dan due date. Pengujian unggah lampiran tugas memastikan file berhasil masuk ke bucket storage task_attachments dan URL lampiran tersimpan pada kolom attachment_url. Pengujian komentar tugas memverifikasi setiap komentar masuk ke tabel comments dengan task_id, user_id, dan created_at yang sesuai.

Skenario anggota diuji dengan membuka InviteMemberModal, melakukan pencarian profil melalui api.profiles.search, lalu menambahkan anggota ke proyek dan memverifikasi baris baru masuk ke project_members. Skenario meeting mencakup pembuatan meeting melalui NewMeetingModal dan pengujian panggilan send-meeting-email edge function. Skenario kecerdasan buatan dijalankan dengan membuka CreateProjectWithAIModal, memasukkan deskripsi proyek, jumlah anggota, dan tanggal deadline, lalu memastikan sistem memanggil AIService.generateProject dan mengembalikan struktur proyek beserta milestone dan tugas sesuai antarmuka. Fitur AIProjectInsightsPanel diuji dengan memicu analyzeProjectHealth berdasarkan data tugas proyek saat ini, sementara chatWithWorkspace diuji untuk memastikan respons AI menyertakan konteks proyek aktif secara benar. Skenario ekspor PDF dijalankan dengan menekan tombol Export pada ProjectDetailPage dan MeetingDetailPage, lalu memastikan sembilan fungsi generator PDF menghasilkan dokumen terunduh dengan kop perusahaan, header tabel berwarna biru, dan footer Dicetak oleh sistem dashboard Bitora Protocol yang konsisten.

4.7.2	Pengujian Black Box

Pengujian kotak hitam memperlakukan sistem sebagai kotak hitam tanpa melihat kode sumber internal. Penguji hanya memasukkan data melalui antarmuka pengguna dan mengamati keluaran yang dihasilkan. Skenario pertama adalah pengujian form input. Form login diuji dengan memasukkan email kosong, password kosong, format email invalid, dan kombinasi email password yang salah untuk memastikan pesan error muncul dari Supabase Auth sesuai kondisi. Form pembuatan proyek diuji dengan mengosongkan field name wajib dan memverifikasi bahwa proyek tidak berhasil tersimpan. Form tugas diuji dengan memberikan judul tugas dan membiarkan deskripsi serta prioritas default untuk memastikan nilai default MEDIUM diterapkan pada basis data. Field due date diuji dengan memasukkan tanggal yang sudah lewat untuk memastikan tugas tetap tersimpan meskipun pada halaman daftar tugas ditandai sebagai overdue.

Pengujian akses data menggunakan dua akun pengguna berbeda. Penguji membuat akun A sebagai OWNER dan membuat proyek P1, lalu mengundang akun B sebagai MEMBER. Kemudian akun B diuji: pada halaman Projects, B hanya boleh melihat proyek P1 dan tidak boleh melihat proyek lain milik akun A yang tidak mengikutkannya sebagai anggota. Aksi penghapusan proyek oleh akun B harus gagal secara diam-diam dari sisi antarmuka (tidak ada tombol hapus yang tersedia), dan jika dipaksakan melalui modifikasi DevTools tetap harus ditolak oleh RLS. Pengujian peran ADMIN dilakukan dengan mengubah peran suatu akun menjadi ADMIN dan memverifikasi bahwa halaman /admin menampilkan daftar seluruh pengguna, seluruh proyek, serta seluruh meeting tanpa memandang kepemilikan proyek.

Skenario edge case meliputi pemuatan aplikasi ketika koneksi internet terputus pada saat auth check berlangsung, pemuatan ulang halaman di tengah sesi login, dan pemulihan sesi ketika storage autentikasi Supabase mengalami korupsi. Skenario terakhir sangat penting karena diatasi langsung oleh logika clearSupabaseAuthStorage pada authStore yang menghapus kunci localStorage dengan pola sb-*-auth-token ketika getSession timeout terdeteksi, sehingga aplikasi tidak selamanya terjebak pada layar Loading Bitspace. Pengujian unggah file juga dilakukan dengan file berukuran besar dan file dengan ekstensi yang tidak diizinkan untuk memastikan pesan error yang informatif muncul dari lapisan Supabase Storage tanpa menyebabkan crash pada frontend.

4.7.3	Pengujian Validasi

Pengujian validasi bertujuan memastikan bahwa data yang masuk ke sistem selalu konsisten dan sesuai aturan bisnis. Validasi dilakukan pada tiga tingkatan yang secara berurutan adalah validasi UI di sisi browser, validasi service sebelum query dijalankan, dan validasi database melalui constraint serta RLS. Tiga tingkatan ini saling melengkapi sehingga kesalahan yang lolos dari satu lapisan dapat ditangkap oleh lapisan berikutnya.

Validasi UI diterapkan pada form dengan memanfaatkan atribut HTML required dan pemeriksaan sederhana sebelum melakukan submit ke API. Contohnya, pada NewProjectModal field nama proyek tidak boleh kosong. Pada TaskModal field title divalidasi panjang minimumnya, field due date divalidasi format tanggal, dan field assignee divalidasi untuk memastikan ID anggota yang dipilih benar-benar ada. Pada form undang anggota, sebelum api.projects.addMember() dipanggil, divalidasi bahwa pengguna tujuan belum terdaftar sebagai anggota proyek guna menghindari pelanggaran primary key composite pada tabel project_members. Validasi serupa diterapkan untuk pencarian global: query hanya dikirim jika panjang keyword minimal 2 karakter, dan debounce diterapkan untuk menghindari request spam saat pengguna mengetik dengan cepat.

Validasi service dilakukan sebelum membangun query Supabase. Fungsi requireAdminOrOwner() dan requireOwner() telah dijelaskan sebelumnya sebagai validasi hak akses. Selain itu, validasi pemetaan data (mapping) dari snake_case ke camelCase juga menangani nilai null dengan aman, misalnya properti assignee pada tugas hanya diisi jika hasil join ke profil tidak null, dan attachment_url dibiarkan undefined jika tidak ada lampiran. Pada modul AIService, validasi yang lebih ketat diterapkan melalui validateAndMapResponse, yang memastikan setiap output AI memiliki struktur sesuai antarmuka AIGeneratedProject, AIGeneratedMilestone, dan AIGeneratedTask sebelum dikembalikan ke komponen. Nilai seperti priority yang tidak sesuai dengan daftar enum akan di-fallback ke MEDIUM, estimatedDays di-clamp ke rentang 1-100, dan milestoneIndex yang melebihi panjang milestone di-set undefined agar tidak menyebabkan kesalahan index out of bounds pada saat pengolahan data selanjutnya.

Validasi database merupakan tahap terakhir dan terkuat dalam tiga lapisan validasi. Constraint NOT NULL diterapkan pada kolom-kolom kunci seperti projects.name dan tasks.title untuk mencegah nilai kosong masuk ke penyimpanan. Foreign key constraint dengan on delete cascade memastikan integritas relasional data turunan terjaga ketika proyek atau tugas dihapus. Constraint CHECK pada tipe ENUM memastikan hanya nilai legal yang tersimpan ke dalam kolom. RLS berfungsi sebagai validasi otorisasi akhir: setiap baris data yang akan dibaca, diubah, atau dihapus selalu dinilai berdasarkan policy yang memeriksa identitas auth.uid() dan relasinya dengan data. Kombinasi ketiga lapisan validasi ini memastikan integritas data Bitspace tetap terjaga meskipun terjadi kesalahan implementasi di salah satu lapisan.

4.8	Hasil Implementasi

Setelah melewati seluruh tahapan implementasi dan pengujian, sistem Bitspace berhasil dibangun sebagai aplikasi manajemen proyek modern yang terintegrasi penuh dengan kecerdasan buatan. Fitur utama sistem terbagi menjadi sembilan domain yang semuanya telah diimplementasikan dan berjalan sesuai rancangan. Domain autentikasi dan otorisasi berhasil diimplementasikan melalui Supabase Auth dengan tiga tingkatan peran pengguna (OWNER, ADMIN, MEMBER), RLS PostgreSQL, dan state management React Context yang mendukung persistensi sesi, timeout recovery pada kondisi storage korup, serta alur pemulihan password terintegrasi.

Domain manajemen proyek mendukung CRUD proyek, pengelompokan status proyek ACTIVE dan ARCHIVED, integrasi field AI untuk generator proyek otomatis, serta perhitungan statistik turunan (total tasks, completed, overdue) secara langsung pada saat query. Domain manajemen tugas menyediakan alur kerja Kanban dengan lima status (BACKLOG, TODO, IN_PROGRESS, REVIEW, DONE), tiga prioritas, penugasan anggota, sub-tugas melalui parent_task_id, lampiran file, komentar, dan drag-and-drop untuk pembaruan status. Domain manajemen milestone mendefinisikan target capaian beserta tanggal jatuh tempo, menghitung progres otomatis berdasarkan persentase tugas selesai, dan memungkinkan penutupan milestone.

Domain meeting menyimpan data meeting lengkap, mengirim notifikasi email melalui Edge Function Deno, serta mendukung ringkasan AI berupa JSONB yang berisi executive summary, keputusan kunci, dan daftar action item yang dapat dikonversi menjadi tugas baru. Domain activity log berfungsi sebagai audit trail otomatis untuk setiap operasi create, update, dan delete pada entitas bisnis, sehingga semua perubahan dapat ditelusuri siapa yang melakukan, kapan, dan detail perubahannya dari metadata JSONB. Domain kecerdasan buatan (AI) mengintegrasikan enam kapabilitas utama yang semuanya berjalan terhadap Google Gemini 2.5 Flash: generator rencana proyek otomatis, breakdown sub-tugas, analisis kesehatan proyek dengan skor risiko dan rekomendasi, summarization meeting, generator laporan sprint dalam format Markdown, serta chat AI workspace yang selalu merujuk pada konteks data proyek aktif.

Domain ekspor laporan menyediakan sembilan jenis laporan PDF dengan format cetak konsisten dan rapi untuk kebutuhan dokumentasi formal proyek. Terakhir, domain admin terpisah menyediakan dashboard khusus ADMIN untuk mengelola seluruh pengguna, proyek, dan meeting di seluruh aplikasi. Secara non-fungsional, arsitektur BaaS yang dipilih menghasilkan deployment yang sederhana: aplikasi frontend dapat di-build menjadi bundle statis melalui npm run build dan diunggah ke penyedia static hosting mana pun (seperti Vercel, Netlify, atau Supabase Storage), sementara backend dikelola sepenuhnya oleh platform Supabase. Skalabilitas horizontal ditangani otomatis oleh Supabase sehingga tim pengembang tidak perlu mengkonfigurasi load balancer atau replikasi database secara manual. Dengan spesifikasi implementasi ini, Bitspace siap digunakan untuk skala tim kecil hingga menengah sebagai sistem pendukung kolaborasi proyek yang modern dan terukur.
